How does it work?

  1. LinkedIn (port 4000) loads a reCAPTCHA script from Google (port 5000). The Google server records the serving time, client key, and HTTP referrer. A “Script served” event appears below.
  2. The script adds a hidden iframe containing a Google document. That document has the CSP rule frame-ancestors 'self' localhost:5000. The LinkedIn page on port 4000 has a different origin and is not allowed to embed it.
  3. The browser blocks the embedding and sends a report itself. The iframe document’s CSP header names the collector using report-uri. The page does not send this POST through JavaScript.
  4. The Google collector receives the report and displays it here. Each correlation card connects the script GET to its report POST. The elapsed time is measured between the two server-side events.

Each script request gets a unique tracking_correlation_nonce_… token. The script passes it to the iframe, whose document includes it in the collector URL. This connects each report to a specific script request, even across multiple tabs.

Blocking the iframe is intentional. In the report, disposition: "enforce" means the policy was enforced; violated-directive identifies the rule. The script-sample field is normally empty here because the violation concerns document embedding, not a code fragment. LinkedIn and Google are simulated locally.
